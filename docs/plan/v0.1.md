# CodeModeKit v0.1 Plan

**Status:** Draft under active review  
**Last updated:** 2026-08-09

## Outcome

An SDK consumer can build an MCP server that aggregates multiple upstream MCP servers and exposes a small Code Mode surface to an LLM client. The LLM calls `run_typescript`; the submitted TypeScript can invoke tools from any configured upstream server through a namespaced `tools` API; and the final bounded result is returned to the LLM.

Consumers can configure upstream servers directly or load their configuration from an Agent Plugin package. The SDK constructs and manages the MCP clients from that configuration.

## Primary acceptance scenario

1. An application constructs `CodeMode` with multiple MCP-backed tool sources and a sandbox.
2. The MCP providers connect to the configured upstream MCP servers and discover their tools.
3. The SDK combines the discovered tools into one normalized catalog and makes them available to sandboxed code through unambiguous `tools` namespaces.
4. The application exposes `CodeMode` through an MCP server with a `run_typescript` tool.
5. An LLM client calls `run_typescript` with model-authored TypeScript.
6. The SDK compiles the TypeScript and executes it in the sandbox.
7. Calls made through `tools` cross the trusted bridge and invoke the corresponding upstream MCP tools.
8. The execution result, or a useful bounded diagnostic, is returned to the LLM client.

The release is successful when this flow works in a documented example without application-specific glue inside the SDK.

## Proposed v0.1 vertical slice

The smallest implementation slice is:

- `CodeMode` orchestration facade;
- `CodeCompiler` with TypeScript compilation and model-useful diagnostics;
- `CodeSandbox` interface and a QuickJS/WASM implementation;
- `ToolBridge` for correlated sandbox-to-host calls;
- normalized tool schema and namespaced addressing;
- `McpToolProvider` composition for discovery and invocation across multiple upstream MCP servers;
- SDK-owned MCP client construction and connection lifecycle;
- direct declarative configuration for stdio and Streamable HTTP, with legacy HTTP+SSE compatibility;
- Agent Plugins 1.0 `mcp.json` loading with per-server failure isolation;
- MCP adapter exposing `run_typescript`;
- one end-to-end example and conformance test covering the primary acceptance scenario.

## Out of scope for the first vertical slice

- OpenAPI and direct local-function provider implementations, unless needed to validate the provider abstraction;
- additional sandbox implementations;
- transparent MCP Apps/UI projection for upstream MCP servers;
- MCP Tasks augmentation for `run_typescript` or transparent upstream task projection;
- persistent catalogs, OAuth, secrets management, or connection administration;
- semantic tool search;
- formal MCP-native skill delivery;
- exposing Agent Skills discovered in Agent Plugin packages to the LLM;
- a graphical frontend.

## Decisions already inherited from the architecture

- TypeScript-first public API and model-authored language.
- `CodeMode`, `CodeCompiler`, `CodeSandbox`, `ToolBridge`, and `ToolProvider` remain separate boundaries.
- QuickJS/WASM is the first sandbox.
- Credentials, unrestricted networking, and host access do not enter the sandbox.
- The model-facing MCP surface is intentionally small, beginning with `run_typescript`.
- Tool documentation uses progressive disclosure rather than injecting the complete catalog into model context.
- `search_tools` is enabled by default as a deterministic bounded fallback and may be explicitly disabled by consumers with complete maintained skills.
- v0.1 aggregates multiple upstream MCP servers.
- Every tool source has a unique configured `name` that becomes its stable top-level `tools` namespace.
- Source and tool names are preserved exactly; generated code uses bracket notation for segments that are not valid TypeScript identifiers.
- The SDK constructs an official TypeScript SDK `Client` for each upstream MCP server and owns connect and close behavior.
- v0.1 supports MCP's standard stdio and Streamable HTTP transports plus legacy HTTP+SSE compatibility.
- v0.1 targets Node.js 20+ and ESM, uses the split MCP TypeScript SDK v2 packages, and may ship against an exact-pinned beta rather than waiting for stable v2.
- Upstream MCP clients explicitly use automatic modern-to-legacy protocol negotiation. The guaranteed matrix tests MCP `2026-07-28`, legacy `2025-11-25`, stdio, Streamable HTTP, and the legacy SSE client path; earlier SDK-supported revisions are best effort.
- The registration adapter composes with a consumer-owned MCP v2 server but does not own or guarantee that server's downstream transport.
- Upstream MCP configuration can be supplied directly or through an Agent Plugins 1.0 package.
- v0.1 loads Agent Plugins from consumer-supplied local root paths; plugin distribution and installation are consumer responsibilities.
- Partial upstream connection failure produces an operational degraded state rather than failing the whole Code Mode server.
- The server starts degraded even with zero healthy sources and reconnects each unavailable source with bounded exponential backoff and jitter.
- Reconnection atomically restores a source's catalog but never automatically replays a failed tool call.
- `run_typescript.code` is compiled as an async function body with top-level `await`, explicit `return`, and no implicit last-expression result.
- `CodeMode.run` resolves to a success/failure union, and execution failures are returned to the LLM as actionable, source-mapped, bounded diagnostics.
- Model-visible failures use stable SDK-owned error codes; compiler and provider codes are preserved only as secondary diagnostic context, and consumers must tolerate new SDK codes.
- v0.1 ships finite defaults for source size, active compute time, total wall time, per-tool time, sandbox memory, tool-call count and concurrency, bridge volume, final output, and logs; trusted consumers may configure them, but the model-facing tool cannot.
- One root cancellation signal fans out through sandbox and provider work. Progress is optional, monotonic, bounded, and summarized at the outer execution level rather than transparently forwarding nested upstream progress.
- `CodeMode` requires an explicit host-side tool policy. It authorizes every validated nested call before dispatch, treats upstream annotations as untrusted hints, and fails closed; v0.1 does not use MCP elicitation to resume a suspended sandbox.
- The sandbox exposes only a versioned allowlist of safe globals plus `tools` and bounded `console`; it has no imports, package loading, dynamic code generation, or ambient host APIs.
- Each sandbox tool call resolves to `{ content, structuredContent? }`; opaque provider `_meta` remains host-side, and provider-declared execution errors become catchable sanitized exceptions.
- Raw provider JSON Schema is the runtime authority. TypeScript types are conservative generated guidance; same-document references are supported, remote references are never fetched, and only tools with invalid or unenforceable schemas are quarantined.
- Normalization retains unknown MCP metadata and source provenance losslessly; sandbox-visible data and downstream protocol projection are separate concerns.
- v0.1 does not transparently proxy upstream MCP Apps/UI. It preserves the definition metadata, result metadata, extension data, and provenance required by a later extension-aware projection layer, while keeping app-only tools out of the model-facing catalog.
- Code Mode, MCP Apps, MCP Tasks, and future MCP Skills are separate projections. Consumers may register direct tools and Apps beside the Code Mode adapter; protocol-native behavior is not inferred from a tool invoked inside `run_typescript`.
- `McpToolProvider` is the only production provider in v0.1. A private in-memory provider and shared conformance suite prove the core is provider-neutral without creating supported local-tool behavior or stabilizing a custom-provider API.
- A later v2 composes MCP, local-function, and OpenAPI tool sources in the same runtime and catalog.

## Planning status

The v0.1 architecture and scope questions raised during design review are resolved. Exact TypeScript signatures and other implementation-level details remain intentionally subject to prototype evidence.

## MCP extension projection risk

Wrapping upstream tool calls behind one downstream `run_typescript` tool is not a transparent MCP proxy.

For MCP Apps in particular:

- UI linkage and visibility live in each upstream tool definition's `_meta.ui`;
- UI resources use source-scoped `ui://` URIs that a downstream host would try to read from the Code Mode server;
- app-only tools must remain hidden from the model while remaining callable by the associated View;
- the View expects the original `CallToolResult`, including result `_meta`;
- upstream extension capability negotiation may depend on downstream host support;
- one TypeScript execution may call several UI-enabled tools or transform their results, leaving no obvious single UI to present.

v0.1 stops at lossless preservation. It retains unknown definition and result metadata plus source provenance in trusted host-side representations, but does not rewrite resource URIs, proxy UI resource reads or app calls, or claim transparent MCP Apps support. Opaque `_meta` does not enter model context merely because it survived normalization.

A later extension-aware adapter may implement end-to-end capability mapping, visibility enforcement, resource routing, and complete View results without changing the provider or sandbox contracts. See `docs/architecture/mcp-extension-projection.md` and ADR 0008.

## Milestones

### M0: Contract spike

- Specify the normalized tool, provider, compiler, sandbox, bridge, and result contracts.
- Specify the supported JSON Schema dialect behavior, validator boundary, conservative TypeScript projection, and per-tool quarantine diagnostics.
- Prove that unknown MCP definition and result metadata round-trips through internal normalization without entering the model-visible projection by default.
- Demonstrate a hard-coded sandbox-to-host asynchronous tool call.
- Compile an async TypeScript function body with model-useful source locations.
- Define and conformance-test the versioned safe-global allowlist.
- Define and conformance-test default execution limits, byte accounting, queueing, log truncation, and limit-specific diagnostics.
- Define and conformance-test root cancellation, terminal-state races, provider abort propagation, and summarized progress mapping across supported MCP transports.
- Specify the model-visible and trusted diagnostic projections.
- Define the initial SDK error-code catalog and conformance mappings from compiler, sandbox, provider, and adapter failures.
- Specify direct and Agent Plugin configuration inputs.
- Lock the exact MCP SDK prerelease, Node.js baseline, explicit protocol-negotiation mode, and guaranteed compatibility matrix.
- Specify the mandatory tool-policy contract, explicit policy helpers, annotation trust rules, fail-closed behavior, and policy diagnostics.
- Specify connection failure, reconnect, and shutdown behavior.
- Specify the source-health and startup-report contracts.
- Specify deterministic local search ranking, response bounds, catalog-revision behavior, and summary-versus-TypeScript projections.
- Build a private deterministic in-memory provider and a shared provider conformance suite without exposing it as a v0.1 product feature.

### M1: Upstream MCP vertical slice

- Discover and combine tools from multiple upstream MCP servers.
- Compile runtime validators and generated TypeScript declarations for discovered schemas without resolving remote references.
- Construct and manage exact-pinned official MCP v2 clients using automatic protocol negotiation over stdio, Streamable HTTP, and legacy HTTP+SSE.
- Load and validate upstream configuration from an Agent Plugin `mcp.json`.
- Generate the sandbox `tools` surface from the normalized catalog.
- Invoke tools from different upstream servers during one model-authored TypeScript execution.
- Prove one mixed-provider execution using an MCP source and the private in-memory conformance fixture in the same catalog.
- Return a structured execution result and useful errors.
- Keep the catalog operational when one configured upstream is unavailable.
- Reconnect a failed source and atomically restore its tools without restarting the Code Mode server.

### M2: Code Mode MCP adapter

- Expose `run_typescript` from a downstream MCP server.
- Expose bounded `search_tools` by default with an explicit consumer opt-out.
- Compose on a consumer-owned MCP server without taking ownership of unrelated direct tools, resources, Apps, or server lifecycle.
- Propagate cancellation, bounds, and sanitized errors.
- Map a supplied downstream progress token to bounded outer execution progress without exposing nested upstream tokens.
- Advertise `run_typescript` conservatively as potentially destructive and open-world and `search_tools` as read-only.
- Prove the complete flow with an MCP client integration test.

### M3: Usable SDK release

- Publish a documented server example.
- Scaffold a runnable one-file server with dependency installation enabled by default.
- Optionally package that server as an Agent Plugins 1.0 component with a companion skill and catalog-derived TypeScript references.
- Add conformance, security-boundary, and failure-path tests.
- Stabilize the smallest public API needed by the example.
- Keep the custom-provider seam internal or explicitly experimental until real local and OpenAPI providers supply v2 design evidence.
- Document unsupported behavior and deferred decisions.

## Exit criteria

- A new consumer can reproduce the example from documentation.
- The downstream MCP client sees `run_typescript` without seeing every upstream tool declaration.
- The downstream MCP client sees `search_tools` by default; one bounded query returns deterministic active-tool matches and exact callable TypeScript without exposing app-only or quarantined tools.
- Disabling `search_tools` removes only that fallback and leaves `run_typescript`, generated skill content, and the internal catalog unchanged.
- The consumer can register unrelated direct MCP tools and resources on the same server without routing them through Code Mode.
- TypeScript executed through `run_typescript` can call tools from at least two configured upstream MCP servers in one execution.
- The same core execution path can call one MCP tool and one private in-memory fixture tool in a single authored program, with no MCP types or transport behavior required by the fixture.
- `run_typescript` supports top-level `await` and explicit `return`, returns `undefined` when no return executes, and never implicitly returns the final expression.
- A compile error, sandbox exception, or uncaught tool error reaches the LLM with an actionable message, original-code location when applicable, bounded logs, and a correlation identifier.
- Model-visible diagnostics use the documented SDK code for their failure class while retaining safe compiler or upstream codes in secondary fields; conformance tests verify representative mappings.
- Diagnostic sanitization removes secrets and host internals without collapsing the error into a generic message.
- Static imports, dynamic imports, `require`, ambient network and filesystem access, host process access, and dynamic code generation are unavailable and produce actionable diagnostics.
- Unknown MCP `_meta` and extension fields survive internal normalization with their source provenance intact.
- Sandbox tool results contain normalized rich `content` and optional typed `structuredContent`, but no opaque `_meta`; an MCP `isError: true` is catchable and becomes an actionable tool diagnostic when uncaught.
- Tool inputs are validated against the authoritative declared schema before provider dispatch. Results always receive structural, serialization, and bounds validation, and declared output schemas validate `structuredContent`.
- Same-document schema references work without network access. A valid but imprecisely representable schema generates conservative TypeScript containing `unknown` rather than disabling the tool.
- A tool with an invalid or runtime-unenforceable schema is absent from the active sandbox catalog, returns `TOOL_SCHEMA_UNSUPPORTED` when addressed through stale code, and appears in bounded catalog diagnostics without disabling valid siblings.
- App-only upstream tools do not appear in the model-facing catalog, and v0.1 is documented as not providing transparent MCP Apps/UI passthrough.
- Duplicate upstream tool names are handled deterministically and tested.
- Agent Plugin server and tool names containing hyphens are preserved and callable through bracket notation.
- Direct configuration covers stdio and Streamable HTTP, with legacy SSE covered by a compatibility test.
- The release targets Node.js 20+ ESM and records the exact MCP SDK beta against which it passed conformance.
- Compatibility tests cover MCP `2026-07-28` over stdio and Streamable HTTP, legacy `2025-11-25` negotiation, and the legacy SSE client path; no test implies a guarantee for every earlier protocol revision.
- The Code Mode adapter registers on a consumer-owned MCP v2 server without taking ownership of its downstream transport.
- An Agent Plugin containing multiple valid MCP entries configures the same runtime without manual translation.
- The consumer can load that plugin by passing its installed local root path; the SDK performs no network or installation work.
- One invalid or unavailable plugin MCP entry does not disable valid sibling entries.
- Partial source failure produces a structured degraded startup report, and calls to that source fail with `SOURCE_UNAVAILABLE`.
- Zero-source startup remains operational, background reconnection restores a recovered source, and failed calls are not replayed.
- Default source, compute, wall-time, tool-time, memory, call-count, concurrency, tool-result, aggregate-bridge, final-result, and log limits match ADR 0013 and can be overridden only by trusted consumer configuration.
- Concurrency above eight queues without exceeding the total-call or wall-time bounds. Oversized non-log data fails explicitly; logs preserve bounded head and tail records with a truncation marker.
- Timeout, memory, and volume limits cancel or reject outstanding work where possible, clean up the sandbox deterministically, and return the documented stable SDK code.
- Caller cancellation terminates sandbox work, rejects queued calls, signals active providers, does not mark a source unhealthy, and yields `EXECUTION_CANCELLED` if a response channel remains available.
- A completion-versus-cancellation race commits exactly one terminal outcome, progress stops afterward, and no cancelled or timed-out tool call is automatically replayed.
- Progress is emitted only when requested, uses an increasing outer sequence without a fabricated total, and rate-limits sanitized messages to the ADR 0014 bounds.
- Construction without a tool policy fails. The example uses an explicit `allowAllToolCalls()` helper, while conformance tests prove allow, deny, callback failure, cancellation, and concurrent queueing behavior.
- Every nested call is validated before policy evaluation and reaches its provider only after an allow decision. A denial or unavailable policy fails closed as catchable `TOOL_APPROVAL_DENIED` without affecting source health.
- The default MCP adapter exposes conservative annotations for `run_typescript` and read-only annotations for `search_tools`, but it does not mistake outer host dispatch for proof of per-call authorization.
- v0.1 never restarts model-authored code to satisfy mid-execution MCP elicitation, so earlier side effects cannot be replayed by an approval round trip.
- No upstream credentials or ambient host capabilities are present in the sandbox.
- The shared provider conformance suite covers discovery, schemas, rich results, sideband retention, diagnostic mapping, cancellation, atomic catalog replacement, and independent failure for both MCP and the private test provider where applicable.
- v0.1 documents `McpToolProvider` as its only supported production provider and does not present the private fixture as local-tool support or promise a stable custom-provider interface.
